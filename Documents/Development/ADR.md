# Architecture Decision Records

## ADR-1: UniTask
**작성일**: 2025-12-06

**배경**:
프로젝트에서 비동기 처리가 필요할 것으로 예상:
- 외부 라이브러리 연동 (ex. Addressables, LevelPlay)
- Non-MonoBehaviour 클래스에서의 비동기 작업 (ex. 데이터/리소스/Scene 관리)

**결정**:
UniTask를 프로젝트의 비동기 처리 표준으로 사용

**근거**:
- Struct 기반 Zero Allocation으로 모바일 GC 부담 최소화
- Unity 생명주기 통합 및 Coroutine 양방향 변환 지원
- Unity에 최적화된 async/await 지원 
- R3와 통합 설계되어 리액티브 프로그래밍과 시너지

**Notes**:
- UniTask의 Addressables 지원(AsyncOperationHandle 전용 ToUniTask 오버로드)은 UniTask.Addressables asmdef에 별도 정의됨. Addressables와 함께 사용하는 asmdef는 반드시 UniTask.Addressables를 참조에 추가할 것. 누락 시 IEnumerator 오버로드로 fallback되어 런타임 에러 발생. 
(2026-03-08)

## ADR-2: R3
**작성일**: 2025-12-06

**배경**:
프로젝트에서 복잡한 이벤트 처리 필요:
- UI 업데이트 및 데이터 바인딩
- 여러 이벤트 조합 및 필터링 (ex. 드래그 입력 처리)
- 비동기 이벤트 플로우 관리

기존 UniRx는 개발 중단되었으며, class 기반 GC 발생 및 Unity 6 호환성 문제 존재. 
R3는 이를 해결한 후속 라이브러리.

**결정**:
R3를 리액티브 프로그래밍 라이브러리로 사용

**근거**:
- Struct 기반 Zero Allocation으로 모바일 GC 부담 최소화
- UniRx 대비 성능 개선 및 Unity 6 호환
- UniTask와 통합 설계되어 시너지
- 이벤트 흐름 관리 용이

## ADR-3: Addressables
**작성일**: 2025-12-06

**배경**:
프로젝트에서 리소스 관리 필요:
- 스킨, 이펙트, 사운드 등 다양한 에셋 로딩
- 모바일 빌드 사이즈 최적화
- 추후 원격 컨텐츠 업데이트 가능성 고려

기존 Resources 폴더 방식은 느린 로딩 속도, 모든 에셋 빌드 포함으로 인한 메모리 비효율 및 빌드 사이즈 증가 문제 존재.

**결정**:
Unity Addressables를 리소스 관리 시스템으로 사용

**근거**:
- 필요한 에셋만 선택적 로드로 모바일 빌드 사이즈 및 메모리 최적화
- 원격 에셋 업데이트로 빌드 없이 컨텐츠 추가 가능
- 에셋 번들 자동 관리로 개발 생산성 향상

## ADR-4: Localization
**작성일**: 2025-12-06

**배경**:

**결정**:

**근거**:

- 하드코딩 대비 유지보수 및 번역 관리 효율적
- Addressables 기반으로 필요한 언어 에셋만 선택적 로드 기능 추가 가능
- 런타임 언어 변경 지원

## ADR-5: New Input System
**작성일**: 2025-12-06

**배경**:
프로젝트에서 입력 처리 필요:
- 모바일 타겟이지만 PC 에디터에서 개발
- 터치/마우스 입력 통합 지원
- 코드 내 입력 키 하드코딩 방지

기존 Old Input System은 코드에 키 매핑을 직접 명시해야 하며, 플랫폼별 입력 처리 분기가 복잡함.

**결정**:
Unity New Input System을 사용

**근거**:
- Input Actions 에셋으로 입력 설정을 데이터로 관리
- 터치/마우스 입력을 단일 액션으로 통합 처리
- PC 에디터에서 모바일 입력 테스트 용이

## ADR-7: VContainer
**작성일**: 2026-02-21

**배경**:
씬 전환 시 발생하는 GC Spike로 인한 프리징을 최소화해야 함.
근본적인 해결을 위해서는 씬 활성화 전 무거운 초기화 작업을 분산 실행할 수 있어야 하며,
이를 위해 씬 내 오브젝트에 의존하는 초기화 로직을 씬 생명주기로부터 분리할 필요가 있음.

또한 현재 전역 시스템이 각기 다른 방식의 Singleton 패턴으로 관리되고 있어, 의존성 관리 방식의 일관성이 부족함:
오브젝트 간 의존성을 명시적이고 일관된 방식으로 관리하는 구조가 필요함.

**결정**:
VContainer를 DI 컨테이너로 도입하고, 전역 시스템 및 씬 단위 의존성 관리를 통합.

**근거**:
- 의존성을 외부에서 주입하는 구조로, 초기화 로직이 씬 생명주기에 종속되지 않음
- 기존 Singleton 패턴을 VContainer의 생명주기 관리로 대체하여 일관성 확보
- UniTask, R3 등 기존 스택과 통합 지원
- Zenject 대비 경량이며 Unity 6 호환성 안정적

## ADR-8: GitHub Actions
**작성일**: 2026-04-04

**배경**:
Repository가 Public으로 전환될 경우 발생할 유료 에셋 라이선스 이슈로 에셋을 저장소에서 분리하게 됨.
이로 인해 새 환경에서 프로젝트를 실행하려면 에셋을 수동으로 설치해야 하는 구조가 됨.
자동화된 빌드 환경에서 이 과정을 처리하고, 추가로 기존에 예정 중이었던 테스트 자동화 환경을 미리 구축.

**결정**:
GitHub Actions를 CI/CD 도구로 사용

**근거**:
- 별도 서버 구성 없이 GitHub 저장소와 네이티브 통합
- game-ci 등 Unity 특화 Action 생태계 활용 가능
- 현재 프로젝트 규모에서 무료 플랜으로 충분

## ADR-9: Aseprite Live MCP
**작성일**: 2026-08-31

**배경**:
게임에 필요한 픽셀 아트를 직접 그리기엔 숙련도가 낮아 결과물의 품질이 기대에 미치지 못함.
기존에는 이미지 생성 AI로 픽셀아트를 만든 뒤 Aseprite에서 수작업으로 다듬었고, 그 가공 단계가 병목이었음.
AI의 도움을 받을 방법을 찾던 중, 에이전트가 실행 중인 Aseprite를 직접 조작하는 방식을 확인.

필요한 것은 양방향 작업. 에이전트의 편집이 화면에 즉시 나타나고, 사람이 직접 고친 내용을 에이전트가 다시 읽을 수 있어야 함.
Aseprite MCP 서버는 다수 존재하나 대부분 배치 모드로 동작함. 파일을 대상으로 Aseprite를 새로 띄우고 작업 후 종료하는 방식이라, 사람이 열어 둔 문서와는 무관하게 동작하며 위 조건을 만족하지 못함.

**결정**:
oaktreegames/aseprite-live-mcp (MIT)를 아트 제작용 MCP 서버로 사용

**근거**:
- 실행 중인 Aseprite 인스턴스를 조작하므로 편집 결과를 즉시 확인하고 이어서 지시 가능
- Unity 스프라이트시트와 .meta를 한 동작으로 생성하며 슬라이스별 피벗이 포함됨
- run_lua를 제공하여 준비된 툴에 없는 조작도 Lua로 직접 수행 가능
- app.transaction 기반이라 에이전트의 편집이 사용자의 Undo 스택에 함께 쌓임
- MIT 라이선스로 포크 및 자체 구현 시 참고가 자유로움

**Notes**:
- 스타 수가 매우 적고 커밋 이력이 짧은 개인 프로젝트. 이를 인지하고 채택했으며 종속되지 않는 선에서만 사용. 산출물은 평범한 PNG와 .meta이므로 도구가 사라져도 만들어 둔 아트는 그대로 사용 가능하며, 역할이 Aseprite를 MCP로 노출하는 것에 한정되므로 같은 기능의 다른 서드파티로 교체 가능
- 패키지가 mcp>=1.10.0으로만 의존성을 걸어 두어 mcp 2.x가 설치되면 import에 실패함. 실행 인자에 --with "mcp<2"를 지정해 우회 중
- 채택 전 동일 아키텍처(WebSocket 브리지)를 자체 스파이크로 검증했으므로, 필요 시 포크하거나 직접 구현 가능. 실제로 동일 구조의 자체 구현을 예정 중
